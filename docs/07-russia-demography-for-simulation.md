# Демография РФ для синтетической симуляции

## Назначение документа

Этот документ задаёт проверяемые демографические ориентиры для симуляции игровой лояльности X5 на 1 000–10 000 синтетических пользователей. Он не описывает клиентскую базу X5 и не заменяет данные программы лояльности. Его задача — сделать синтетическую популяцию правдоподобной по возрасту, полу, типу населённого пункта, федеральному округу, составу домохозяйства и цифровой готовности.

Числа ниже имеют разные даты наблюдения, потому что последняя доступная официальная статистика по показателям выходит в разные годы:

- общая численность и урбанизация — на 1 января 2025 года;
- подробная половозрастная структура и федеральные округа — на 1 января 2024 года;
- домохозяйства и семейные ячейки — ВПН-2020;
- цифровая готовность — обследование Росстата за 2025 год.

Для защиты и отчёта всегда нужно показывать дату базы рядом с показателем.

## Короткий вывод

Для основной симуляции корректнее брать население `18+`, но не считать каждого взрослого потенциальным пользователем приложения X5. Сначала создаётся демографическая популяция, затем отдельными вероятностями моделируются доступ к цифровым сервисам, участие в программе лояльности, активность в приложении и попадание в пилот.

Сегмент «взрослые с детьми до 3 лет» из [синтетического профиля команды](04-customer-segments.md) нельзя задавать как взаимоисключающую возрастную группу и нельзя принимать за национальную долю. Наличие ребёнка — пересекающийся признак жизненного этапа. Доля `26–28%` среди синтетических пользователей приложения может использоваться только как гипотеза целевого oversampling, но не как демографический факт.

- семейных ячеек всего — `35 466 004`;
- семейных ячеек с детьми младше 18 лет — `15 532 802`;
- семейных ячеек с детьми младше 3 лет — `2 908 553`;
- ячейки с детьми младше 3 лет составляют `8,20%` всех семейных ячеек или `18,72%` семейных ячеек с детьми младше 18 лет;

Для пользовательской симуляции лучше сначала сгенерировать домохозяйства и семейные признаки, а затем выбрать взрослых пользователей. Для упрощённого PoC допустима условная вероятность `has_child_under_3`, но её нужно пометить как калибруемое допущение и проверять в нескольких сценариях.

## 6. Как использовать данные в симуляции

### Рекомендуемая последовательность генерации

1. Сгенерировать возрастную группу взрослого пользователя по долям `18+` из раздела 2.
2. Условно от возраста сгенерировать пол и тип населённого пункта по долям внутри возрастной группы.
3. Добавить федеральный округ. Национальные веса допустимы только для общероссийского сценария; для пилота нужны веса выбранной географии.
4. Добавить домохозяйство и жизненный этап: один человек, пара, дети младше 18 лет, ребёнок младше 3 лет. Эти признаки пересекаются с возрастом и не заменяют его.
5. Сгенерировать цифровую готовность, прежде всего условно от возраста. Пол и тип поселения можно использовать как дополнительные поправки, но нельзя одновременно перемножать все маргинальные проценты и называть результат официальной совместной вероятностью.
6. Отдельно сгенерировать `loyalty_member`, `app_user` и `pilot_eligible`. Пока нет данных X5, эти вероятности являются сценарными параметрами.
7. Только после этого генерировать поведение: частоту визитов, размер корзины, категории, маржу, чувствительность к промо, склонность к механикам и риск фрода.

### Три обязательных среза результата

| Срез | Для чего нужен |
| --- | --- |
| Национально взвешенная популяция | Проверить, что демография генератора не перекошена |
| Цифровая/app-eligible популяция | Показать аудиторию, которая потенциально может участвовать в мобильной механике |
| Целевой сегмент пилота | Оценить эффект выбранной механики, например среди семей с маленькими детьми |

Если целевой сегмент намеренно oversampled, нужно вывести как результаты внутри сегмента, так и результат после обратного взвешивания. Иначе эффект узкой аудитории будет ошибочно выдан за эффект по всей базе.

### Корреляции, которые нельзя игнорировать

- возраст связан с цифровой готовностью;
- возраст и пол связаны между собой в старших группах;
- возраст связан с вероятностью наличия маленьких детей;
- сельское/городское проживание связано с цифровым поведением;
- состав домохозяйства связан с корзиной и частотой покупок;
- активные пользователи приложения — не случайная выборка населения.

Для PoC достаточно условных таблиц и калибровки весов. Для более строгой версии подойдут iterative proportional fitting, калиброванные вероятностные модели или синтетические домохозяйства. Не следует создавать искусственную точность без исходных микроданных X5.

## 7. Что остаётся допущением, а не демографическим фактом

Росстат не даёт нужных для этого кейса параметров поведения клиентов X5. Следующие величины должны иметь статус `ASSUMPTION`, `PUBLIC_PROXY` или `TO_VALIDATE`:

- проникновение карты лояльности и приложения X5;
- частота визитов и средний чек по сегментам;
- валовая и вкладная маржа корзины;
- вероятность принять и выполнить конкретный челлендж;
- причинный uplift частоты покупок;
- чувствительность к размеру награды;
- доля погашенных и просроченных баллов;
- каннибализация обычных покупок;
- частота возвратов и фрода;
- вероятность успешной реферальной конверсии;
- торговое покрытие X5 по округам и типам поселений.

Каждый такой параметр должен иметь диапазон `low/base/high`, источник или владельца валидации и влияние на итоговую чистую дополнительную маржу.

## 8. Практические правила для проекта

- Не использовать категорию «взрослые с вредными привычками» как демографический класс. Покупки алкоголя/сигарет можно моделировать отдельным receipt-derived признаком и использовать как safety-метрику, eligibility-фильтр или основание для нейтральной механики; задания не должны стимулировать рост такого потребления.
- Не выводить ФИО, адрес или точную геолокацию в рейтинге. Использовать opt-in, аватар/псевдоним и достаточно крупную анонимную лигу.
- Не считать цифровую готовность доказательством любви к аватарам, рейтингам или рефералам. Предпочтение механики проверяется экспериментом.
- Не использовать национальные веса для оценки бизнес-эффекта без поправки на реальную клиентскую и магазинную базу.
- Не называть результаты синтетической симуляции прогнозом. Это scenario analysis и проверка связности допущений; причинный эффект подтверждает только пилот с контролем.
